# naming.md — 命名規則と「AIが引き出すための4つの手がかり」

> 「しまう」ためではなく「後で引き出す」ために設計します。
> 将来ノートを探すとき、人もAIも必ず次の4つのどれかを手がかりにします。

## AIが引き出すための4つの手がかり

| 手がかり | 何か | 例 |
|---|---|---|
| **type（種類）** | 何のノートか | 調査 / 手順書 / 計画 / 検討 / 概念 / リファレンス / 管理 …（**語は下の語彙表で確定**） |
| **when（時期）** | いつのものか | 作成日・関連する時期 |
| **topic（主題）** | 何についてか | 疾患名 / 研究テーマ / 案件名 |
| **status（状態）** | どの状態か | 常時更新 / 運用中 / 参照用 / 進行中 / 保留 / 完了（**この6語だけ**。下の語彙表） |

この4つがノートに記録されていれば、「進行中の(status) 膝OA研究の(topic) 先月以降の(when) 決定事項(type)を出して」がそのまま通ります。

## ファイル名の型

```
YYYY-MM-DD-種類-主題.md
```

例：
```
2026-01-20-会議録-研究ミーティング.md
2026-01-18-手順書-統計解析の環境構築.md
2026-01-15-調査-変形性膝関節症に対する運動療法のエビデンス.md
```

日付を先頭に置くと、自動で時系列に並び、名前も衝突しません。

- **`reports/` に .md を作るときは必ずこの型**
- **日付は作成日**。イベントの日ではない（イベント日は本文と frontmatter の `topic` に書く）
- **主題に半角スペースと `_` を使わない**。区切りが要るときは「の」で繋ぐか詰める
- **frontmatter の `type:` はファイル名の「種類」と同じ語にする**（`report` と `レポート` の混在を作らない）
- **改名するときは Vault 全体を `Grep` して、`[[wikilink]]` とパス参照を一式直す**（片方だけ直すとリンクが切れる）

### 「種類」に使う語（この中から選ぶ）

| 種類 | 使うとき |
|---|---|
| `調査` | 問いに対して調べて答えを出したもの（文献・制度・価格の検証を含む） |
| `手順書` | 手順・コード本体・セットアップ方法 |
| `計画` | 日程・段取りが確定したもの（旅行・イベント） |
| `検討` | 候補を比べて未決のもの |
| `週次レビュー` | `/weekly` が出すレビュー。**これだけ主題を書かない**（`YYYY-MM-DD-週次レビュー.md`。日付が対象期間を表すため） |
| `会議録` / `提案` / `意思決定` | それぞれの通り |

迷ったら `調査`。新しい語を増やすときはこの表に足す。

## ノート冒頭の frontmatter

各ノートの先頭に、AIが構造として読めるメタ情報を持たせます。

```markdown
---
type: 会議録
status: 進行中
date: 2026-01-20
topic: 研究ミーティング
tags: [研究, 膝OA]
---
（ここから本文）
```

`status` が引き出しで最も効きます（「進行中だけ」「完了を除く」が一発）。**ただし語が揺れると grep で引けなくなるので、下の語彙表から選びます。**

### `type:` と `status:` に使う語

**`type:`** — 置き場所で使う語が違う。

| 置き場所 | 使う語 |
|---|---|
| `reports/` | ファイル名の「種類」と**同じ語**（上の表から。`調査` `手順書` `計画` `検討` `週次レビュー` …） |
| `wiki/` | `概念`（疾患・テーマの知識）／`リファレンス`（ツール・仕様の引き表）／`管理`（index・lint・open_questions などの運用ページ） |
| `wiki/moc/` | `MOC`（テーマ地図。**このフォルダ専用**。役割が上の3語のどれとも違うため独立させている） |
| `daily/` | `daily` ／ `Memory.md` は `memory` ／ `Home.md` は `home` |

> [!warning] 同じ意味の語を増やさない
> `report` と `レポート`、`レビュー` と `週次レビュー` のような**英語・カタカナ・略称の混在を作らない**。上の表に無い語を使いたくなったら、**表に足してから**使う。

**`status:`** — この6語から選ぶ。

| status | 意味 |
|---|---|
| `常時更新` | 更新し続けるページ（`wiki/` の正本・`Memory.md`・`index`） |
| `運用中` | 仕組み・アプリとして動いているもの |
| `参照用` | 完成して読むだけのもの |
| `進行中` | まだ動いている案件 |
| `保留` | **動かさないと決めた**もの（理由を1行書く。`停滞` とは書かない → `rules/mistakes/status.md`） |
| `完了` | 決着したもの（`完成` `実行済み` `決定済み` `実施済み` `確定` は使わず `完了` に寄せる） |

過去分は**触れたついでに直す**（一括では直さない）。

### `date:` の意味は置き場所で変わる

| 置き場所 | `date:` の意味 | 理由 |
|---|---|---|
| `reports/` `daily/` — **ファイル名に日付があるもの** | **作成日**（ファイル名の日付と同じにする） | その日の記録なので、後から書き足しても日付は動かない |
| `wiki/` `Home.md` `Memory.md` — **常時更新するもの** | **最終更新日**（中身を書き換えたら今日の日付に上げる） | Vault をクラウドドライブに置くと、**同期のたびにファイルの更新日時が書き換わる**ので、OS の更新日時では「どのページが古いか」を判定できない。`date:` だけが頼り |

> [!warning] `wiki/` を書き換えたら `date:` も上げる
> 上げ忘れると週次レビュー Step 3（`grep -l "^date: <過去7日>" wiki/*.md`）から漏れ、その週の更新が無かったことになる。

## タグの付け方（増やしすぎない）

- 種類で分ける：`#topic/膝OA` `#status/進行中` `#project/学会発表`
- `/` で区切ると階層として畳めます。
- **5つ以上のノートで使うものだけ** タグ化する（1〜2件のタグはノイズ）。

## 原則

- フォルダで細かく分類しない。命名と `[[リンク]]` で繋ぐ。
- 既存ノートを一括で直そうとしない。**次に作る1枚からこの型で**。過去分は触れたついでに直す。
