# 日本語ビジネスデッキの作り方

このスキルは「作る」より前に**合意を取る**ことに重心がある。長い成果物は、書き上げてから構成を直すと手戻りが本文全体に及ぶ。だから型と構成の2回、必ず立ち止まる。

## 前提の確認

環境によって使える道具が違う。**最初に確認してから方針を決める**。

```bash
which node soffice libreoffice pdftoppm; python3 -c "import pptx, PIL; print('python-pptx + PIL OK')"
```

- `node` があれば pptxgenjs が使える（組み込みの `pptx` スキルの手順が使える）
- **無ければ python-pptx で組む。** その場合このスキルの `assets/deck_lib.py` を使う
- `soffice` が無ければ PDF 化できない → **`scripts/render_qa.py` で目視QAする**（後述）

macOS に PowerPoint 本体があっても、AppleScript 経由のPDF書き出しは**タイムアウトして返らないことがある**。1回試して返らなければ諦めて同梱レンダラに切り替える。待ち続けない。

## 手順

### 1. 素材を集め、正本を1つに決める

同じ事実が複数のノートに散っていることが多い。**どれが正本かを先に決める**。数字が食い違っていたら、外部を調べる前に「それぞれどこから来たか」を辿る。抽出値・推定値と一次資料を対等に並べない。

読み手が誰か（何を知っていて、何を判断したいのか）を明確にする。これが型の選定を決める。

### 2. 型を提示し、選んでもらう

`references/frameworks.md` を読み、**その素材と読み手に噛み合う型を3〜4つに絞って提示する**。全部並べない。各型について「向くとき」と「デメリット」を必ず両方書き、推奨案を明示する。

そのうえで `AskUserQuestion` で選んでもらう。同時に聞くとよいのは **資料の使い方**（送って読ませる／話しながら見せる／両方）。1枚あたりの文字量と、説明をスピーカーノートに寄せるかどうかが変わるため。

型を勝手に決めて進めない。ここは相手の資料であって、こちらの作品ではない。

### 3. 構成を出して合意を取る

**本文を書く前に、全スライドの一覧を出す。** 各行に「見出し（＝そのまま主張になる1文）」と「載せる証拠」を書く。表形式が読みやすい。

あわせて**判断が要る点を2〜3個**挙げる。「削るならどこか」「どこまで踏み込むか」「未確認の数字をどう扱うか」など。ここで潰しておかないと、完成後に構成ごと直すことになる。

合意が取れるまで生成に進まない。

### 4. 生成する

`assets/deck_lib.py` をスクラッチパッドにコピーし、それを `import` する `build.py` を書く。ライブラリは版面（16:9 / 13.333×7.5インチ、左右マージン0.75）と、テキストボックス・カード・バッジ・表・脚注・ページ番号のヘルパを持つ。使い方は `assets/deck_lib.py` の冒頭のdocstringにある。

守ること:

- **見出しは「1文の主張」にする**（アサーション・エビデンス型）。「Aの結果」ではなく「Aは2026年に無料経路が閉じた」。その下に置く証拠は1枚につき1つ。日本語の主張文は長いので、見出しは26pt前後・2行までを見込む
- **通しのモチーフを1つ決める。** 前回は「判定バッジ」（右上の色付きピル）だった。内容と意味が結びつくものを選ぶ。**装飾用の色帯・タイトル下の下線は使わない**（AI製に見える上に情報を持たない）
- **ダーク地とライト地を使い分ける。** 表紙・結論・最終ページをダークにすると締まる
- **文字量は使い方に合わせる。** 話しながら見せるなら本文は薄くし、説明は全スライドのスピーカーノートに書く

日本語固有の落とし穴と版面の数値は `references/layout.md` にまとめてある。**生成前に必ず読む。** フォント選定、絵文字を使わない理由、脚注とページ番号の衝突など、毎回同じ場所で事故る。

### 5. 目視QAして直す

**1回目のレンダリングには必ず実際の不具合がある。** はみ出し・重なり・余白の偏りを見つけて直す。

```bash
python3 <skill>/scripts/render_qa.py deck.pptx png
```

このスクリプトは pptx を読んで PIL で近似描画し、`png/slide-NN.png` を出したうえで**はみ出しと枠外を機械検出して一覧する**。まず警告をゼロにし、**そのうえで全枚数を実際に画像で見る**。警告が出ないことと、見て良いことは別物。

見るときの優先順位:

1. 文字のはみ出し・切れ（最も多い）
2. 要素の重なり（脚注とページ番号、表と脚注が典型）
3. 余白の偏り（下だけ1.5インチ空く、など）
4. 低コントラスト（ダーク地に濃い色の文字、ライト地に薄い色）
5. 意味を持たない空白カード（項目数がテンプレの枠数に足りていない）

**レンダラは近似である。** フォントは代用され、太字はストロークで擬似的に描かれる。行数とはみ出しの判定は実用上一致するが、字面の印象は実物と違う。PowerPoint で開いた確認を自分でできない場合は、**その旨をはっきり伝える**。

### 6. 納品する

ファイルの置き場所は勝手に決めず、プロジェクトの規約に従う（このユーザーのvaultなら `90_Assets/`、読み取り専用の共有フォルダには絶対に書かない）。渡すときは以下を添える:

- 何枚か、スピーカーノートの有無
- 型と、通しのモチーフとして何を使ったか
- **QAで何を直したか**
- **確認できていないこと**（PowerPoint実物での見え方など）

## 事実の扱い

デッキは他人に渡る。ノートより厳しく扱う。

- **裏の取れていない主張には、スライド上に「要検証」バッジを貼る。** ノート本文の `status/要検証` をスライドで落とさない。読み手は本文の但し書きを読まないが、バッジは見る
- **二次情報の数字は、そのスライドの脚注に「二次情報・要再確認」と書く。** 料金・手数料・税率は契約経路や国で変わる。断定しない
- **推論と事実を混ぜない。** 推論はカードを分けるか色を変えて、「ここは推論であって事実ではない」と明示する。n がいくつかも書く
- **オーナーや関係者の経験・発言を創作しない。** 一人称で出る文（提案文・挨拶）に体験の枠を作ったら、中身は書かずプレースホルダのまま出す
- **時事性のあることは書く前に調べる。** 記憶で書かない

## 同梱ファイル

| ファイル | 中身 | いつ読むか |
|---|---|---|
| `references/frameworks.md` | 構成の型5つ（SCQA／実験レポート／スパークライン／PREP／アサーション・エビデンス）と選び方 | 手順2の前 |
| `references/layout.md` | 版面の数値、日本語固有の落とし穴、色の作り方 | 手順4の前（必ず） |

| `scripts/render_qa.py` | pptx → PNG 近似レンダリング＋はみ出し検出 | 手順5 |
